# リソース

## リソースを宣言する

[リソース](glossary.md#resource) は、データを生成する ([オプションで非同期の](../reference/performance.md#parallelism)) 関数です。リソースを作成するには、その関数に `@dlt.resource` デコレータを追加します。

よく使われる引数:

- `name`: このリソースによって生成されるテーブルの名前。デフォルトでは装飾された関数名になります。
- `write_disposition`: データを宛先にどのようにロードしますか? 現在サポートされているのは、`append`、`replace`、および `merge` です。デフォルトは `append` です。

例:

```py
@dlt.resource(name='table_name', write_disposition='replace')
def generate_rows():
	for i in range(10):
		yield {'id': i, 'example_string': 'abc'}

@dlt.source
def source_name():
    return generate_rows
```

リソースのデータを取得するには、次のようにします:

```py
for row in generate_rows():
    print(row)

for row in source_name().resources.get('table_name'):
    print(row)
```

通常、リソースは [source](source.md) 関数内で宣言され、関連するリソースとグループ化されます。

### スキーマを定義する

`dlt` は、リソースのデータからリソースに関連付けられたテーブルの [スキーマ](schema.md) を推測します。
テーブルと列のヒントを使用して生成プロセスを変更できます。リソースデコレータは次の引数を受け入れます:

1. `table_name`: リソース名と異なる場合のテーブル名。
1. `primary_key` と `merge_key`: これらのヒントを受け取る列の名前を定義します (複合キーが許可されます)。[インクリメンタルローディング](incremental-loading.md)で使用されます。
1. `columns`: データ型、NULL 値可能性、その他のヒントを含む 1 つ以上の列を定義できます。列定義は `TypedDict`: `TTableSchemaColumns` です。以下の例では、`dlt` に、`user` テーブルの列 `tags` (タグのリストを含む) の型が `json` である必要があることを伝えています。つまり、これは JSON/struct としてロードされ、別のネストされたテーブルとしてロードされることはありません。

  ```py
  @dlt.resource(name="user", columns={"tags": {"data_type": "json"}})
  def get_users():
    ...

  # the `table_schema` method gets the table schema generated by a resource
  print(get_users().compute_table_schema())
  ```

:::note
データ項目を入力として受け取り、ヒント値を返す関数である動的ヒントを渡すことができます。これにより、データに応じてテーブルと列のスキーマを作成できます。[こちらの例](#adjust-schema-when-you-yield-data)を参照してください。
:::

<!-- :::tip
一部のリソース引数を [構成と資格情報](credentials) 値としてマークして、`dlt` がそれらを関数に自動的に渡すことができるようにすることができます。
::: -->

### テーブル、列、データに制約を付与する

`schema_contract` 引数を使用して、dlt に [新しいテーブル、データ型、不正なデータ型の処理方法](schema-contracts.md)を指示します。たとえば、これを **freeze** に設定すると、`dlt` は新しいテーブル、列、またはデータ型をスキーマに導入することを許可せず、例外を発生させます。使用可能な契約モードの詳細については、[こちら](schema-contracts.md#setting-up-the-contract)を参照してください。

### ネストされたテーブルのスキーマを定義する

`dlt` は、データ内に存在する場合、[オブジェクトのリスト](destination-tables.md#nested-tables)を格納するための[ネストされたテーブル](schema.md#nested-references-root-and-nested-tables)を作成します。
このようなテーブルのスキーマは、`@dlt.resource` の `nested_hints` 引数で定義できます:

```py
import dlt

@dlt.resource(
    nested_hints={
        "purchases": dlt.mark.make_nested_hints(
            columns=[{"name": "price", "data_type": "decimal"}],
            schema_contract={"columns": "freeze"},
        )
    },
)
def customers():
    """Load customer data from a simple python list."""
    yield [
        {
            "id": 1,
            "name": "simon",
            "city": "berlin",
            "purchases": [{"id": 1, "name": "apple", "price": "1.50"}],
        },
    ]
```

ここでは、`purchases` リストの `price` フィールドを 10 進数型に変換し、その中の列のリストをロックするためのスキーマコントラクトを設定します。
ネストされたヒント辞書を生成するために、便利な関数 `dlt.mark.make_nested_hints` を使用します。
この関数はそのまま使用しても構いません。

`purchases` リストは `customers__purchases` という名前のテーブルとして保存されることに注意してください。
ネストされたヒントを宣言する際は、ネストされたフィールド名を指定するだけです。
ネストが深い場合、つまり各 `purchase` に `coupons` リストが適用されている場合、クーポンにヒントを適用し、`customers__purchases__coupons` テーブルスキーマを定義できます:

```py
import dlt

@dlt.resource(
    nested_hints={
        "purchases": {},
        ("purchases", "coupons"): {
            "columns": {"registered_at": {"data_type": "timestamp"}}
        }
    },
)
def customers():
    ...
```

ここでは、`("purchases", "coupons")` を使用して、深さ2のリストを見つけ、`registered_at`列のデータ型を`timestamp`に設定しています。これは、ネストされたヒント辞書を直接使用することで実現しています。
`purchases` に空のヒントリストを指定していることに注意してください。**親ヒントが空であっても、すべて指定する必要があります。現在、不足しているパス要素は自動的に追加されません**。

`nested_hints` は主に列ヒントとスキーマコントラクトの設定に使用でき、これらはルートテーブルの場合と全く同じように機能します。
* `file_format` は効果がありません（まだ実装されていません）。
* `write_disposition` は期待通りに動作しますが、意図しない結果（つまり、ルートテーブルが `append` であるにもかかわらず、ネストテーブルを `replace` に設定できるなど）が発生します。
* `references` は期待通りに [テーブル参照](schema.md#table-references-1) (アノテーション) を作成します。
* `primary_key` と `merge_key`: **これらを設定すると、ネストテーブルが通常のテーブルに変換され、書き込み処理、ファイル形式などが別々になります。**
[これにより、データ内に存在する自然な主キーと外部キーを使用して、カスタムテーブル関係を作成できます。](schema.md#generate-custom-linking-for-nested-tables)

:::tip
[REST API ソース](../dlt-ecosystem/verified-sources/rest_api/basic.md) は `nested_hints` 引数も受け入れます。

リソース作成後に [apply_hints](#set-table-name-and-adjust-schema) を使用してネストされたヒントを適用できます。
:::

### Pydanticでスキーマを定義する

代わりに、[Pydantic](https://pydantic-docs.helpmanual.io/) モデルを使用してスキーマを定義することもできます。たとえば:

```py
from pydantic import BaseModel
from typing import List, Optional, Union

class Address(BaseModel):
    street: str
    city: str
    postal_code: str

class User(BaseModel):
    id: int
    name: str
    tags: List[str]
    email: Optional[str]
    address: Address
    status: Union[int, str]

@dlt.resource(name="user", columns=User)
def get_users():
    ...
```

テーブル列のデータ型は、Pydantic フィールドの型から推測されます。これらは、データからスキーマが自動的に生成される場合と同じ型変換を使用します。

Pydantic モデルは、データ検証ツールとして [スキーマのコントラクト](schema-contracts.md)と適切に統合されます。注意事項は:

- `Optional` 型のフィールドは `nullable` としてマークされます。
- `Union` 型のフィールドは、ユニオンにリストされている最初の型 (`None` ではない) に変換されます。たとえば、`status: Union[int, str]` は `bigint` 列になります。
- `list`、`dict`、およびネストされた Pydantic モデル フィールドは `json` タイプを使用します。つまり、ネストされたテーブルを作成する代わりに、データベースに JSON オブジェクトとして保存されます。

Pydanticモデルを設定することでこれを上書きすることができます:

```py
from typing import ClassVar
from dlt.common.libs.pydantic import DltConfig

class UserWithNesting(User):
  dlt_config: ClassVar[DltConfig] = {"skip_nested_types": True}

@dlt.resource(name="user", columns=UserWithNesting)
def get_users():
    ...
```

`"skip_nested_types"` は、スキーマから `dict`/`list`/`BaseModel` 型のフィールドを省略するため、dlt はこれらのフィールドに対してネストされたテーブルを作成するデフォルトの動作に戻ります。

単純な型を検証する `RootModel` はサポートされていません。このような検証を自分で追加できます。[データ フィルタリングのセクション](#filter-transform-and-pivot-data) を参照してください。

### データを複数のテーブルにディスパッチする

単一のリソースから複数のテーブルにデータをロードできます。最も一般的なケースは、それぞれ異なるデータ スキーマを持つ、異なるタイプのイベントのストリームです。これに対処するには、`dlt.resource` で `table_name` 引数を使用できます。テーブル名を関数として渡し、データ項目を引数として、`table_name` 文字列を戻り値として渡すことができます。

たとえば、GitHub リポジトリ イベントをロードするリソースは、`issue`、`pull request`、および `comment` イベントを別々のテーブルに送信したいと考えています。イベントのタイプは、「type」フィールドにあります。

```py
# send item to a table with name item["type"]
@dlt.resource(table_name=lambda event: event['type'])
def repo_events() -> Iterator[TDataItems]:
    yield item

# the `table_schema` method gets the table schema generated by a resource and takes an optional
# data item to evaluate dynamic hints
print(repo_events().compute_table_schema({"type": "WatchEvent", "id": ...}))
```

より高度なケースでは、リソース関数のコード内でデータを直接異なるテーブルにディスパッチすることができます:

```py
@dlt.resource
def repo_events() -> Iterator[TDataItems]:
    # mark the "item" to be sent to the table with the name item["type"]
    yield dlt.mark.with_table_name(item, item["type"])
```

### リソースをパラメータ化する

他の関数と同様に、リソース関数に引数を追加できます。以下では、`generate_rows`リソースをパラメータ化して、要求した行数を生成します:

```py
@dlt.resource(name='table_name', write_disposition='replace')
def generate_rows(nr):
    for i in range(nr):
        yield {'id': i, 'example_string': 'abc'}

for row in generate_rows(10):
    print(row)

for row in generate_rows(20):
    print(row)
```

:::tip
一部のリソース引数を [構成と資格情報](credentials)の値としてマークして、`dlt` がそれらを関数に自動的に渡すことができるようにすることができます。
:::

### `dlt.transformer` でリソースを処理する

あるリソースから別のリソースにデータをフィードできます。最も一般的なケースは、1 つのエンドポイントでオブジェクト (つまり、ユーザー) のリストを返し、別のエンドポイントでユーザーの詳細を返す API がある場合です。これに対処するには、ユーザーのリストを取得するリソースと、リストから項目を受け取ってプロファイルをダウンロードする別のリソースを宣言します。

```py
@dlt.resource(write_disposition="replace")
def users(limit=None):
    for u in _get_users(limit):
        yield u

# Feed data from users as user_item below,
# all transformers must have at least one
# argument that will receive data from the parent resource
@dlt.transformer(data_from=users)
def users_details(user_item):
    for detail in _get_details(user_item["user_id"]):
        yield detail

# Just load the users_details.
# dlt figures out dependencies for you.
pipeline.run(users_details)
```

上記の例では、`users_details` は `users` リソースのデフォルト インスタンスからデータを受信します (`limit` は `None` に設定されています)。**pipe |** 演算子を使用してリソースを動的にバインドすることもできます。

```py
# You can be more explicit and use a pipe operator.
# With it, you can create dynamic pipelines where the dependencies
# are set at run time and resources are parametrized, i.e.,
# below we want to load only 100 users from the `users` endpoint.
pipeline.run(users(limit=100) | users_details)
```

:::tip
トランスフォーマーは、**yield** だけでなく、**return** 値も許可されており、**async** 関数と [**async generators**](../reference/performance.md#extract) を装飾できます。以下では、async 関数を装飾し、2 つのポケモンの詳細を要求します。HTTP 呼び出しは、httpx ライブラリを介して並列に行われます。

```py
import dlt
import httpx


@dlt.transformer
async def pokemon(id):
    async with httpx.AsyncClient() as client:
        r = await client.get(f"https://pokeapi.co/api/v2/pokemon/{id}")
        return r.json()

# Get Bulbasaur and Ivysaur (you need dlt 0.4.6 for the pipe operator working with lists).
print(list([1,2] | pokemon()))
```
:::

### スタンドアロンリソースを宣言する

スタンドアロン リソースは、config と secrets の値を受け入れるモジュール (内部関数ではない) のトップレベルの関数で定義されます。さらに、`standalone` フラグが指定されている場合は、装飾された関数のシグネチャと docstring が保持されます。`dlt.resource` は装飾された関数をラップするだけで、ユーザーは実際のリソースを取得するためにラッパーを呼び出す必要があります。以下では、使用前に呼び出す必要がある `filesystem` リソースを宣言します。

```py
@dlt.resource(standalone=True)
def fs_resource(bucket_url=dlt.config.value):
  """List and yield files in `bucket_url`."""
  ...

# `filesystem` must be called before it is extracted or used in any other way.
pipeline.run(fs_resource("s3://my-bucket/reports"), table_name="reports")
```

スタンドアロンは、デコレートされた関数に渡される引数に応じて動的な名前を持つ場合があります。たとえば:

```py
@dlt.resource(standalone=True, name=lambda args: args["stream_name"])
def kinesis(stream_name: str):
    ...

kinesis_stream = kinesis("telemetry_stream")
```
`kinesis_stream` リソースの名前は **telemetry_stream** です。

### 並列および非同期リソースを宣言する

複数のリソースを並列スレッドまたは非同期IOで抽出できます。
同期リソースでこれを有効にするには、リソースデコレータで `parallelized` フラグを `True` に設定します:

```py
@dlt.resource(parallelized=True)
def get_users():
    for u in _get_users():
        yield u

@dlt.resource(parallelized=True)
def get_orders():
    for o in _get_orders():
        yield o

# users and orders will be iterated in parallel in two separate threads
pipeline.run([get_users(), get_orders()])
```

非同期ジェネレータは他のリソースと同時に自動的に抽出されます:

```py
@dlt.resource
async def get_users():
    async for u in _get_users():  # Assuming _get_users is an async generator
        yield u
```

詳細については、[抽出パフォーマンス](../reference/performance.md#extract)をご覧ください。

## リソースをカスタマイズする

### データのフィルタリング、変換、ピボット

リソースには、アイテムごとに評価される変換をいくつでも添付できます。使用可能な変換タイプは:

- **map** - データ項目を変換します (`resource.add_map`)。
- **filter** - データ項目をフィルタリングします (`resource.add_filter`)。
- **yield map** - イテレータを返すマップ (つまり、1 つの行から複数​​の行が生成される場合があります - `resource.add_yield_map`)。

例: APIエンドポイントからユーザーのリストを読み込むリソースがあります。これをカスタマイズして:

1. `user_id == "me"` のユーザーを削除します。
2. ユーザーデータは匿名化されます。

こちらが私たちのリソースです:

```py
import dlt

@dlt.resource(write_disposition="replace")
def users():
    ...
    users = requests.get(RESOURCE_URL)
    ...
    yield users
```

変換を定義してデータをロードするスクリプトは次のとおりです。:

```py
from pipedrive import users

def anonymize_user(user_data):
    user_data["user_id"] = _hash_str(user_data["user_id"])
    user_data["user_email"] = _hash_str(user_data["user_email"])
    return user_data

# add the filter and anonymize function to users resource and enumerate
for user in users().add_filter(lambda user: user["user_id"] != "me").add_map(anonymize_user):
    print(user)
```

### 生成されたテーブルのネストレベルを減らす

ネストされたテーブルを生成し、辞書を列に平坦化するときに、`dlt` がどこまで深く進むかを制限できます。デフォルトでは、ライブラリは制限なく、ネストされたすべてのリストに対してネストされたテーブルを生成し、降下します。

:::note
`max_table_nesting` はオプションなのでスキップできます。この場合、dlt はソースで指定されている場合はそれを使用します。そうでない場合は、最大ネスト レベルが 1000 であるデフォルト値にフォールバックします。
:::

```py
import dlt

@dlt.resource(max_table_nesting=1)
def my_resource():
    yield {
        "id": 1,
        "name": "random name",
        "properties": [
            {
                "name": "customer_age",
                "type": "int",
                "label": "Age",
                "notes": [
                    {
                        "text": "string",
                        "author": "string",
                    }
                ]
            }
        ]
    }
```

上記の例では、ネストされたテーブルを 1 レベルだけ生成します（ネストされたテーブルにネストされたテーブルはありません）。一般的な設定:

- `max_table_nesting=0` はネストされたテーブルを生成せず、辞書を列にフラット化しません。ネストされたデータはすべて JSON として表されます。
- `max_table_nesting=1` はルート テーブルのネストされたテーブルのみを生成し、それ以上は何も生成しません。ネストされたテーブル内のすべてのネストされたデータは JSON として表されます。

```py
resource = my_resource()
resource.max_table_nesting = 0
```

いくつかのデータ ソースには、MongoDB データベースなど、非常に深いネストを持つ半構造化ドキュメントが含まれる傾向があります。実際の経験では、`max_nesting_level` を 2 または 3 に設定すると、最も明確で人間が判読できるスキーマが生成されます。

### 大規模データからのサンプル

リソースが REST API から数千ページのデータやデータベース テーブルから数百万行を読み込む場合、サンプル データを含むデータセットをすばやく確認し、変換などをテストするために、その一部だけをサンプリングしたい場合があります。これを行うには、`add_limit` メソッドを呼び出して、リソース (またはソース) によって生成される項目の数を制限します。このメソッドは、制限に達した後にデータを生成するジェネレーターを閉じます。

以下の例では、無限カウンターから最初の 10 個の項目のみを読み込みます (そうでない場合、カウンターは決して終了しません)。

```py
r = dlt.resource(itertools.count(), name="infinity").add_limit(10)
assert list(r) == list(range(10))
```

:::note
`add_limit` は **レコード数を制限するのではなく**、"yield の数" を制限することに注意してください。リソースの設定方法に応じて、抽出される行数は異なる場合があります。たとえば、このリソースを考えてみましょう:

```py
@dlt.resource
def my_resource():
    for i in range(100):
        yield [{"record_id": j} for j in range(15)]

dlt.pipeline(destination="duckdb").run(my_resource().add_limit(10))
```

上記のコードは、`15*10=150` レコードを抽出します。これは、各反復で 15 レコードが生成され、反復回数を 10 に制限しているために発生します。
:::

あるいは、リソースに時間制限を適用することもできます。以下のコードは、10 秒間抽出を実行し、その時間内に生成されたアイテムの数だけ抽出します。インクリメンタルと組み合わせると、バッチ読み込みや実行時間制限のあるマシンでの読み込みに役立ちます。

```py
dlt.pipeline(destination="duckdb").run(my_resource().add_limit(max_time=10))
```

両方の制限を組み合わせて適用することもできます。この場合、どちらかの制限に達するとすぐに抽出が停止します。

```py
dlt.pipeline(destination="duckdb").run(my_resource().add_limit(max_items=10, max_time=10))
```

`add_limit` に関する注意事項:

1. `add_limit` はどの項目もスキップしません。制限に達した後、データを生成するイテレータ/ジェネレータを閉じます。
2. トランスフォーマーを制限することはできません。生成されたデータセットの不整合を回避するために、トランスフォーマーは受信したすべてのデータを完全に処理する必要があります。
3. 制限が追加された非同期リソースでは、実行によっては制限を超えるアイテムが 1 つ生成されることがあります。この動作は確定的ではありません。
4. リソースに対して add limit を呼び出すと、以前に設定された制限設定が置き換えられます。
5. 時間制限のあるリソースの場合、最初の項目が処理されるとタイマーが開始されます。リソースが順番に処理される場合 (FIFO モード)、各リソースの時間制限も順番に適用されます。デフォルトのラウンドロビン モードでは、時間制限は通常同時に実行されます。

:::tip
`add_limit` の値をパラメータ化していて、無効にする必要がある場合は、`None` または `-1` を設定して制限を無効にすることができます。
また、リソースがアイテムを生成しないように制限を `0` に設定することもできます。
:::

### テーブル名を設定し、スキーマを調整する

リソースのスキーマは、スタンドアロンでもソースの一部でも変更できます。リソースデコレータと同じ引数を取る `apply_hints` というメソッドを探します。当然、このメソッドはリソースからデータが抽出される前に呼び出す必要があります。以下の例では、`users` テーブルをロードする `append` リソースを、`user_id` ごとに更新されたレコードを 1 つだけ保持する [merge](incremental-loading.md#merge-incremental_loading) リソースに変換します。また、`created_at` 列に [インクリメンタルローディングの"last value"](incremental-loading.md#incremental_loading-with-last-value)を追加して、すでにロードされているレコードを再度要求しないようにします。:

```py
tables = sql_database()
tables.users.apply_hints(
    write_disposition="merge",
    primary_key="user_id",
    incremental=dlt.sources.incremental("updated_at")
)
pipeline.run(tables)
```

リソースがデータをロードするテーブルの名前を変更するには、次の操作を行います:

```py
tables = sql_database()
tables.users.table_name = "other_users"
```

### データを生成するときにスキーマを調整する

リソースが実行され、すでにデータが出力されているときに、テーブル名、列、およびその他のスキーマ要素を設定または更新できます。このような変更は、上記の `apply_hints` メソッドと同じように、既存のスキーマとマージされます。実行時にスキーマを調整する理由はたくさんあります。たとえば、Airflow を使用する場合、DAG の作成中に時間のかかる操作 (データベース テーブルの反映など) を避ける必要があるため、DAG の実行時に行う方がよいでしょう。また、列の部分的なヒント (小数点型の精度とスケールなど) を発行して、`dlt` 型の推論を支援することもできます。

```py
@dlt.resource
def sql_table(credentials, schema, table):
    # Create a SQL Alchemy engine
    engine = engine_from_credentials(credentials)
    engine.execution_options(stream_results=True)
    metadata = MetaData(schema=schema)
    # Reflect the table schema
    table_obj = Table(table, metadata, autoload_with=engine)

    for idx, batch in enumerate(table_rows(engine, table_obj)):
      if idx == 0:
        # Emit the first row with hints, table_to_columns and _get_primary_key are helpers that extract dlt schema from
        # SqlAlchemy model
        yield dlt.mark.with_hints(
            batch,
            dlt.mark.make_hints(columns=table_to_columns(table_obj), primary_key=_get_primary_key(table_obj)),
        )
      else:
        # Just yield all the other rows
        yield batch

```

上記の例では、`dlt.mark.with_hints` と `dlt.mark.make_hints` を使用して、最初に抽出された項目の列と主キーを出力します。テーブルスキーマは、`batch` が抽出パイプラインで処理された後、スキーマ コントラクトが適用される前に調整され、データはロード パッケージに保持されます。

:::tip
列を Pydantic モデルとして出力し、動的ヒント (つまり、テーブル名に対するラムダ式) も使用できます。この方法では、`Incremental` を再定義することは避けてください。
:::

### 外部ファイルをインポートする

`with_file_import` でマークされた項目の生成によって、CSV、Parquet、JSONL などの外部ファイルをインポートできます。オプションでインポートされたファイルに対応するテーブル スキーマを渡せます。dlt は
(CSV または Arrow ヘッダーなど)の名前を読んだり、解析したり、正規化したりせず、ファイルをそのまま宛先にコピーしようとします。

```py
import os
import dlt
from dlt.sources.filesystem import filesystem

columns: List[TColumnSchema] = [
    {"name": "id", "data_type": "bigint"},
    {"name": "name", "data_type": "text"},
    {"name": "description", "data_type": "text"},
    {"name": "ordered_at", "data_type": "date"},
    {"name": "price", "data_type": "decimal"},
]

import_folder = "/tmp/import"

@dlt.transformer(columns=columns)
def orders(items: Iterator[FileItemDict]):
  for item in items:
    # copy the file locally
      dest_file = os.path.join(import_folder, item["file_name"])
      # download the file
      item.fsspec.download(item["file_url"], dest_file)
      # tell dlt to import the dest_file as `csv`
      yield dlt.mark.with_file_import(dest_file, "csv")


# use the filesystem core source to glob a bucket

downloader = filesystem(
  bucket_url="s3://my_bucket/csv",
  file_glob="today/*.csv.gz") | orders

info = pipeline.run(orders, destination="snowflake")
```

上記の例では、**my_bucket/csv/today** にあるすべての圧縮された csv ファイルを glob し (`filesystem` 検証済みソースを使用)、ファイル記述子を `orders` トランスフォーマーに送信します。トランスフォーマーはファイルをダウンロードし、抽出パッケージにインポートします。最後に、`dlt` はそれらを Snowflake に送信します (`column` ヒントを使用してスキーマを定義するため、テーブルが作成されます)。

インポートされた `csv` ファイルが `dlt` [デフォルト形式](../dlt-ecosystem/file-formats/csv.md#default-settings) でない場合は、追加の構成を渡す必要があるかもしれません。

```toml
[destination.snowflake.csv_format]
delimiter="|"
include_header=false
on_error_continue=true
```

データからスキーマをスニッフィングできます。つまり、DuckDB を使用して CSV ファイルからテーブル スキーマを推測できます。`dlt.mark.with_file_import` は、実行時にヒントを渡すために使用できる追加の引数を受け入れます。

:::note
* 列を定義しないと、宛先にテーブルは作成されません。`dlt` は引き続きデータのロードを試行するため、事前に適切なテーブルを作成すれば、ロード プロセスは成功します。
* 必要なストレージスペースのコピーと重複を回避するために、可能な場合はハードリンクを使用してファイルがインポートされます。
:::

### リソースを複製して名前を変更する

リソースが汎用的（バケットファイルシステムなど）で、その複数のインスタンス（異なるフォルダのファイルなど）を別々のテーブルにロードしたい場合があります。以下の例では、`filesystem` ソースを使用して、2 つの異なるフォルダから csv を別々のテーブルにロードします:

```py
@dlt.resource(standalone=True)
def fs_resource(bucket_url):
  # list and yield files in bucket_url
  ...

@dlt.transformer
def csv_reader(file_item):
  # load csv, parse, and yield rows in file_item
  ...

# create two extract pipes that list files from the bucket and send them to the reader.
# by default, both pipes will load data to the same table (csv_reader)
reports_pipe = fs_resource("s3://my-bucket/reports") | csv_reader()
transactions_pipe = fs_resource("s3://my-bucket/transactions") | csv_reader()

# so we rename resources to load to "reports" and "transactions" tables
pipeline.run(
  [reports_pipe.with_name("reports"), transactions_pipe.with_name("transactions")]
)
```

`with_name` メソッドは、元のリソース、そのデータ パイプ、および親リソースのデータ パイプのディープ コピーを返します。名前が変更されたクローンは、ロード時に元のリソース (および他のクローン) から完全に分離されます。つまり、別の[リソース状態](state.md#read-and-write-pipeline-state-in-a-resource)が維持され、テーブルにロードされます。

## リソースを読み込む

`dlt.pipeline` オブジェクトには、個々のリソースまたはリソースのリストを渡すことができます。ソース コンテキストの外部にロードされたリソースは、パイプラインの [デフォルトスキーマ](schema.md) に追加されます。

```py
@dlt.resource(name='table_name', write_disposition='replace')
def generate_rows(nr):
    for i in range(nr):
        yield {'id': i, 'example_string': 'abc'}

pipeline = dlt.pipeline(
    pipeline_name="rows_pipeline",
    destination="duckdb",
    dataset_name="rows_data"
)
# load an individual resource
pipeline.run(generate_rows(10))
# load a list of resources
pipeline.run([generate_rows(10), generate_rows(20)])
```

### 特定のリソースのローダーファイル形式を選択する

リソースに使用する特定のローダー ファイル形式を要求できます。

```py
@dlt.resource(file_format="parquet")
def generate_rows(nr):
    for i in range(nr):
        yield {'id': i, 'example_string': 'abc'}
```

上記のリソースは、Parquet ファイルから保存およびロードされます (宛先がサポートしている場合)。

:::note
特別な `file_format`: **preferred** は、宛先で優先される形式を使用してリソースをロードします。この設定は、`run` メソッドに渡される `loader_file_format` に優先します。
:::

### 完全にリフレッシュする

`append` または `merge` のリソースを完全に更新するには、`run` メソッドの `refresh` 引数を `drop_data` に設定します。これにより、テーブルは削除されずに切り捨てられます。

```py
p.run(merge_source(), refresh="drop_data")
```

`merge_source`で[テーブルを完全に削除](pipeline.md#refresh-pipeline-data-and-state)することもできます。:

```py
p.run(merge_source(), refresh="drop_sources")
```
