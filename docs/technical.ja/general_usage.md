## dlt のインポート
`dlt` の基本機能は `import dlt` でインポートされます。これらの機能は以下のとおりです。
1. `dlt.run` でパイプラインを実行する（特定のソースと出力先に対して、抽出→正規化→ロードを実行する）
2. パイプラインを設定する（代替パイプライン名、作業ディレクトリ、スキーマのインポート/エクスポート先フォルダ、各種フラグを指定する）: `dlt.pipeline`
3. ソース（`dlt.source`）とリソース（`dlt.resource`、`dlt.transformer`）をデコレーションする
4. シークレット（`dlt.secrets`）と設定値（`dlt.config`）にアクセスする

## 宛先のインポート
以下の手順でインポートできる組み込みの宛先をいくつかサポートしています。
```python
import dlt
from dlt.destinations import bigquery
from dlt.destinations import redshift
```

インポートされたモジュールは、`run` メソッドまたは `pipeline` メソッドに直接渡すことができます。⛔ また、資格情報やその他の設定を明示的に提供するために呼び出すこともできます（非推奨）。たとえば、`bigquery(Service.credentials_from_file("service.json"))` は、資格情報をモジュールにバインドします。

宛先には `extras` がインストールされている必要があります。インストールされていない場合は、ユーザーフレンドリーなメッセージとともに例外が表示され、インストール方法が示されます。

## ソースのインポート
組み込みソースや提供ソースはなく、配布方法も実装されていません。

☮️ 組み込みソースは `dlt.sources` 名前空間からインポートできます。
⛔ 提供ソースは `dlt init <source> <destination>` 経由で Python コードモジュールとして追加できます。

## デフォルトおよび明示的に設定されたパイプライン
`dlt` をインポートすると、デフォルトのパイプラインが自動的に作成されます。このパイプラインは、設定プロバイダ（`config.toml` または環境変数 - [secrets_and_config.md](secrets_and_config.md) を参照）を介して設定されます。設定が存在しない場合は、デフォルト値が使用されます。

1. パイプラインの名前、デフォルトスキーマの名前（ソース抽出関数によってオーバーライドされていない場合）、およびデフォルトデータセット（出力先）は、**現在のモジュール名** に `dlt_` プレフィックスを付けた値に設定されます。これは、99% の場合、実行中の Python スクリプトの名前です。例: `pipeline.py` の場合、デフォルト名は `dlt_pipeline` です。
2. パイプラインの作業ディレクトリは、(1) ホームディレクトリを持つ非 root ユーザーの場合 (99% の場合): **~/.dlt/pipelines/pipeline name** (2) root ユーザー (Linux/Mac OS): **/var/dlt/pipelines/pipeline name** (3) ホームディレクトリを持たないユーザーの場合: **OS temp dir/dlt/pipelines/pipeline name**` となります。
3. ☮️ システムログレベルは **CRITICAL** (無効) (アルファ版では **WARNING**) となります。
4. その他の設定オプションは設定されないか、デフォルト値になります。
5. ⛔ ユーザーログが有効になります。

パイプラインは、`Pipeline` オブジェクトを返す `dlt.pipeline()` を介して明示的に作成および設定できます。すべてのパラメータはオプションです。パラメータが指定されていない場合は、デフォルトのパイプラインが返されます。オプションの一覧を以下に示します。すべてのオプションは設定可能です。
1. pipeline_name - デフォルトは上記
2. working_dir - デフォルトは上記
3. pipeline_secret - 決定論的ハッシュ用 - デフォルトは乱数
4. destination - インポート先のモジュールまたはモジュール名（文字列を指定できるので設定可能） - デフォルトは None
4. dataset_name - データの保存先となるデータセット名（デフォルト名は後述）
5. import_schema_path - デフォルトは None
6. export_schema_path - デフォルトは None
7. dev_mode - True に設定すると、パイプラインの作業ディレクトリが消去され、データセット名に一意のサフィックス（現在のタイムスタンプ）が付けられます。つまり、`my_data` は `my_data_20221107164856` になります。

> **注意** `secrets_and_config.md` によると、`dlt.pipeline` に渡される引数は設定可能であり、省略された場合は設定プロバイダによって挿入されます。**コード内で明示的に指定された値は、すべての設定プロバイダよりも完全に優先されます**

一部のパイプライン設定は、設定プロバイダ（つまり `config.toml`）経由でのみ設定できます。いくつか興味深い設定があります。
```toml
# Enables the `run` method of the `Pipeline` object to restore the pipeline state and schemas from the destination
restore_from_destination=true
# Stores all schemas in single dataset. When False, each schema will get a separate dataset with `{dataset_name}_{schema_name}
use_single_dataset=true
```

> `dlt.pipeline()` を介して多数のパイプラインが設定されている場合は、単一のスクリプト内に複数のパイプラインを持つことができます。

## デフォルトのスキーマとデフォルトのデータセット名
`dlt` は、スキーマを自動生成し、データがロードされるデータセットに名前を付ける際に、以下のルールに従います。

**スキーマはスキーマ名によって識別されます**

**デフォルト スキーマ** は、パイプライン内で最初に提供または作成されるスキーマです。最初のスキーマは、以下の方法で取得されます。
1. 最初に抽出された `@dlt.source` から取得されます。つまり、`dlt.run(data=spotify(), ...)` を実行し、`spotify` ソースに `spotify` という名前のスキーマがアタッチされている場合、それがデフォルト スキーマとして使用されます。
2. `@dlt.resource` またはイテレータ（リストなど）を抽出した場合は、最初から作成されます（例: `dlt.run(data=["a", "b", "c"], ...)`）。その名前はパイプライン名、またはジェネレーター関数が抽出された場合はジェネレーター関数名になります。（自動命名を賢く行うようにしています。）
3. `run` メソッドまたは `extract` メソッドに `schema` パラメーターを使用して明示的に渡されます。これにより、形式に関係なく、すべてのソースのテーブルがそのスキーマに配置されます。

**デフォルトスキーマ**は、ポイント（2）のようにスキーマ情報なしでデータを抽出する際に使用されます。この場合、デフォルトスキーマは、そのデータから取得したテーブルをアタッチするために使用されます。

パイプラインは複数のスキーマで動作します。別のソースを抽出したり、明示的にスキーマを指定したりした場合、そのスキーマはパイプラインの一部になります。例
```python

p = dlt.pipeline(dataset_name="spotify_data_1")
p.extract(spotify("me"))  # gets schema "spotify" from spotify source, that schema becomes default schema
p.extract(echonest("me").with_resources("mel"))  # get schema "echonest", all tables belonging to resource "mel" will be placed in that schema
p.extract([label1, label2, label3], name="labels")  # will use default schema "spotitfy" for table "labels"
```

> ファイル経由とプログラムの両方でスキーマを操作する方法の詳細については、[working_with_schemas.md](working_with_schemas.md) を参照してください。

### 出力先におけるデータセット名とデータセットレイアウト

`dlt` は、出力先で指定されたデータセットにデータをロードします。BigQuery の場合はネイティブデータセット、Redshift の場合はネイティブデータベーススキーマです。

**デフォルトでは、1 つのデータセットで複数のスキーマを処理できます**。
パイプライン設定オプション `use_single_dataset` は、出力先におけるデータセットレイアウトを制御します。デフォルトでは True に設定されています。この場合、出力先には 1 つのデータセットのみが作成されます。デフォルトのデータセット名はパイプライン名と同じです。データセット名は、`dlt.pipeline`、`dlt.run`、および `Pipeline::load` メソッドに明示的に指定することもできます。
すべてのスキーマのすべてのテーブルがそのデータセットに保存されます。テーブル名には **スキーマ名がプレフィックスとして付加されません**。名前の競合が発生した場合、出力先のテーブルは、スキーマ内で同じ名前を持つすべてのテーブルのフィールドの結合になります。

**スキーマレイアウトごとに1つのデータセットを有効にする**
`use_single_dataset` を False に設定した場合：

**パイプラインに（デフォルトの）スキーマのみが存在する場合**、データはデータセット名でデータセットにロードされます。例：`dlt.run(spotify("me"), dataset_name="spotify_data_1")` は、データセット `spotify_data_1` にデータをロードします。

**パイプラインに複数のスキーマが存在する場合**、データは、デフォルトスキーマの場合は `{dataset_name}`、その他のスキーマの場合は `{dataset_name}_{schema_name}` という名前のデータセットにロードされます。上記の例では、以下のようになります。
1. `spotify` テーブルと `labels` は `spotify_data_1` にロードされます。
2. `mel` リソースは `spotify_data_1_echonest` にロードされます。

`dev_mode` オプション：データセット名には現在のタイムスタンプが接頭辞として付加されます。つまり、`my_data` は `my_data_20221107164856` になります。これにより、非破壊的な完全更新が可能になります。保存先から何も削除/ドロップされません。

## パイプラインの作業ディレクトリと状態
もう一つの基本的な概念は、パイプラインの作業ディレクトリです。このディレクトリには、以下の情報が保存されます。
1. 抽出されたデータと、正規化によって作成されたジョブを含むロードパッケージ
2. 最新の更新を含む現在のスキーマ
3. パイプラインとソースの状態ファイル

パイプラインの作業ディレクトリはユーザーが設定できます。デフォルトについては、上記の**デフォルトおよび明示的に設定されたパイプライン**で説明されています。

### パイプラインの作業ディレクトリを宛先から復元します。

`dlt.pipeline` の `restore_from_destination` 引数を使用すると、宛先から状態とパイプラインのスキーマを復元できます。`dlt` は、状態が宛先に保存されているかどうかを確認し、ダウンロードしてから、必要なすべてのスキーマをダウンロードします。その後、データ抽出を再開できます。

状態は他のデータと共に宛先に保存されます。そのため、パイプラインのすべてのステージが完了した場合にのみ、状態を復元できます。

`dev_mode` フラグが設定されている場合、パイプラインを復元することはできません。

完全更新をトリガーするもう1つの方法は、宛先データセットを削除することです。`dlt` はこれを検出し、パイプラインのローカル作業フォルダをリセットします。

## `dlt` が理解するデータソース
`run` メソッドと `extract` メソッドは、以下のものを理解します。
1. `dlt.source`、`dlt.resource`、およびそれらのリスト
2. JSON シリアル化可能オブジェクト（datetime、decimal、uuid 型を含む）のリスト、イテレータ、ジェネレータ
3. ⛔ panda フレーム、pyarrow テーブルはネイティブに処理されます ☮️ イテレータとして処理されます
4. ☮️ ビルドされたソースを表す `uri` 文字列（`file.json`、`file.parquet`、`s3://bucket/file.json`）

## パイプラインの実行と `dlt.run` + `@source().run` 関数
`dlt.run` + `@source().run` は、デフォルトまたは最後に（`dlt.pipeline` で）設定された `Pipeline` オブジェクトの `Pipeline::run` メソッドへのショートカットです。例については、[create_pipeline.md](create_pipeline.md) を参照してください。

この関数は以下のパラメータを取ります。
1. data - 必須 - 出力先にロードするデータ。`@dlt.source` またはそのリスト、`@dlt.resource` またはそのリスト、イテレータ/ジェネレータ関数またはそのリスト、あるいはイテレータが処理する他の要素を保持する反復可能オブジェクト（リスト）。
2. 出力先
3. データセット名
4. table_name、write_disposition など - データが単一のリソース、イテレータ（ジェネレータ関数など）、または反復可能オブジェクト（リストなど）の場合のみ
5. schema - ソースによって提供されるスキーマまたはデフォルトのスキーマの代わりに使用する `Schema` インスタンス
6. credentials - 資格情報を明示的に指定する場合は、ここで渡します

`run` 関数の動作は以下のとおりです。
1. 正規化またはロードする保留中のデータがある場合、まずこれが実行されます。
2. 成功した場合のみ、さらにデータが抽出されます。
3. 成功した場合のみ、新しく抽出されたデータが正規化され、ロードされます。

extract / normalize / load はアトミックです。`run` は可能な限りアトミックです。

`run` と `load` は、ロードされたパッケージに関する情報を返します。どのデータセットにロードされたか、ジョブのリストなどです。内容はどうすべきか考えさせてください。

> SQL 変換、つまり `dbt` とすべての SQL クエリがコミット済みの `load_ids` のみを考慮する場合、`load` はアトミックです。これは確かに可能です。RASA では実現しましたが、多少の作業が必要です。ローダーのどこかの時点で、完全にアトミックなステージングを実装する必要があるかもしれません。

### 命名規則と正規化
デフォルトのJSON正規化機能は、JSONドキュメントをテーブルに変換します。すべてのキー名（つまり、すべてのテーブルと列）は、設定された命名規則に従って正規化されます。

❗ [詳細はこちら](working_with_schemas.md)

### 開発モード
`dev_mode` フラグが `dlt.pipeline` に渡された場合、
1. パイプラインの作業ディレクトリ（状態、スキーマ、一時ファイル）が完全に消去されます。
2. データセット名に現在のタイムスタンプが接頭辞として付加されます。例: `my_data` は `my_data_20221107164856` になります。
3. パイプラインは出力先から復元されません。

これにより、非破壊的な完全リフレッシュが可能になります。出力先から何も削除/ドロップされません。新しいスキーマを持つ新しいデータセットが作成されます。

### LoadInfo の戻り値
run メソッドは、実際にロードされた内容の情報を含む `LoadInfo` タプルを返します。正確な内容は現在開発中です。現在、以下の情報が含まれています。
1. ロード先情報
2. データセット名
3. ロードされたパッケージ ID のリスト
4. パッケージ ID ごとの失敗したジョブのリスト

これは拡張が必要です。

### 実行例外
`run`、`extract`、`normalize`、`load` メソッドは、パイプライン内のいずれかのステップが失敗した場合に `PipelineStepFailed` 例外を発生させます。失敗したジョブでは例外は発生しません。

## パイプラインランタイムのセットアップ

1. ロギング - `dlt` という名前のロガーを作成します。これは、Python の方法で無効化できます。（`dbt` ロガーは制御不能で混乱を招くため、ここでは省略します。）
2. シグナル - Docker、Kubernetes、cron において、Ctrl + C でパイプラインを正常に停止するために必要なシグナルが処理されます。`dlt` が `streamlit` アプリまたはノートブックの一部として実行される場合、シグナルは処理されません。
3. 未処理の例外 - 未処理の例外はキャッチしませんが、スタンドアロンスクリプトで実行される場合はキャッチする場合があります。
